# Pay With Atoa for Shop - implementation plan

Status: SCOPE ONLY. Nothing built. Plan written 2026-08-30 against
`gocardless-instant-bank-pay-for-shop` v0.1.17 and `square-payment-for-shop` v0.1.24
as precedent, plus Atoa's developer docs (docs.paywithatoa.co.uk) as read that day.

Scope: a new module `pay-with-atoa-for-shop` adding Atoa pay-by-bank as a checkout
payment method. Two phases - hosted redirect, then an on-page dialog - with the shop
owner choosing between them. **No core changes required.**

**Modules touched:** none. One new module, `shop` untouched.
**Core:** nothing. No release, no `core-reconcile` file, no `prisma/` edit.

---

## 0. Two findings that shape the plan

**0.1 - Atoa's Web Client SDK exposes no theme parameter.** Its init object is
`environment`, `paymentRequestId`, `customerDetails` and four callbacks, and nothing
else. Theme colour is a single brand colour set in the Atoa dashboard and applied to
every merchant surface; there is no light/dark pair. So "the on-page modal works in
light and dark mode" splits into a part we own outright and a part we do not - see
§6. We can make everything around the dialog correct in both themes and stop it
looking broken. We cannot repaint its interior.

**0.2 - Atoa's `amount` field has no documented unit.** GoCardless takes pence; Atoa's
reference says only "total payment amount", with a refund minimum of `1`. That is a
hundredfold error in whichever direction it lands, on live orders. Settled by one
sandbox call at stage 1.1, before any conversion helper is written. Nothing else
starts until it is answered and the answer is written into `lib/atoa.ts` as a comment.

## 1. Why no core change is needed (recon summary)

- **The method code is free.** `ShpPaymentMethod` (`modules/shop/lib/types.ts:419`) is
  `'STRIPE' | 'PAYPAL' | 'BANK_TRANSFER' | 'CASH' | (string & {})`. A module
  contributes `ATOA` without shop enumerating it.
- **The extension points already exist and are already used twice.**
  `shop.payment-providers` and `shop.checkout-payment-fields` are collected in
  `modules/shop/lib/payments/registry.ts:22` and
  `modules/shop/lib/checkout-payment-fields.ts`. `lib/modules/extension-points.ts` is
  regenerated by `scripts/generate-module-extension-points.mjs` on every build and dev
  start - registering is a manifest entry, nothing else.
- **The draft-order pattern is solved.** `orderCreation: 'on-payment'` +
  `materialiseDraftOrder` (`modules/shop/lib/checkout-draft.ts`). GoCardless proved it:
  no order row until money is committed, so a shopper who backs out on the bank's page
  leaves nothing in the owner's list. Atoa has the identical problem.
- **The hosted/on-page owner choice is solved.** Square ships it as a stored setting -
  `SquareCardEntry` in `modules/square-payment-for-shop/lib/settings.ts`, column added
  in `migrations/003_card_entry.sql`. Atoa's is the same shape with different words.
- **The confirm route already handles on-payment providers.**
  `modules/shop/app/api/public/checkout/confirm/route.ts:128` calls
  `materialiseDraftOrder` on success and already understands `result.pending` (:78,
  :136). Phase 2 needs no new plumbing there.
- **`atp_` is free** as a table prefix; `pay-with-atoa-for-shop` is free as a module
  name (`modules.json` has 32 entries, none of them Atoa).

Verify test still passes after wiring - `git grep "modules/pay-with-atoa-for-shop" --
':!modules' ':!wiki' ':!.gitmodules'` must return empty.

## 2. Atoa API surface, mapped

Base URL `https://api.atoa.me` for both environments. Auth is
`Authorization: Bearer <accessSecret>` - the key itself is the token, there is no
exchange endpoint. Sandbox is distinguished by which key you send, plus `&env=sandbox`
on status checks (confirm the exact set of calls needing it at stage 1.1).

| Provider contract (`modules/shop/lib/payments/provider.ts`) | Atoa | Note |
|---|---|---|
| `createIntent` -> `approvalUrl` | `POST /api/payments/process-payment` -> `paymentUrl` | Phase 1 |
| `createIntent` -> `clientFields` | same call -> `paymentRequestId` | Phase 2 |
| `getClientFields` | `{ environment }` only | Publishable, order-independent |
| return route | `redirectUrl` + `callbackParams` | Appended as query params |
| `handleWebhook` | `PAYMENTS_STATUS` event, `X-Atoa-Signature` | Hex HMAC-SHA256 of raw body |
| `confirmPayment` | `getPaymentStatus` | Server-side re-check, never the client |
| `refundOrder` | initiate refund, partial supported | **No idempotency key** - see §7.2 |
| `getRefundStatus` | `INITIATED`/`COMPLETED`/`FAILED` | Refunds async; implement it |

**Request fields used on create:** `orderId`, `amount`, `currency`, `customerId`,
`redirectUrl`, `callbackParams`, `expiresIn`, `paymentMethod`, `consumerDetails`,
`metadata`, `notes`. Response: `paymentUrl`, `paymentRequestId`, `qrCodeUrl`,
`qrCodeUrlPng`, `templateUrl` (QR/template unused here).

**Status mapping** (`lib/settle.ts`):

| Atoa | Shop |
|---|---|
| `COMPLETED` | `markOrderPaid` then `fulfillPaidOrder` |
| `PENDING` | `markOrderAwaitingConfirmation` |
| `FAILED` | `markOrderPaymentFailed` |
| `AUTHORIZED`, `CANCELLED` | card-only capture states; unreachable while `PAY_BY_BANK` only |

`AUTHORIZED`/`CANCELLED` still get an explicit branch that logs loudly rather than
falling through - an unhandled status on a payment route is how money goes quiet.
Pay-by-bank has no chargebacks, so the GoCardless chargeback path
(`isPaymentChargedBack`, `settle.ts:36-50`) drops out. A late `FAILED` arriving after
an order is already `PAID` still needs handling.

**Webhook events:** `PAYMENTS_STATUS`, `EXPIRED_STATUS`, `REFUND_STATUS`,
`POS_PAYMENT_STATUS`. We subscribe to the first three; POS is not ours. Endpoints are
registered over the API at `/api/webhook/v2/endpoints`, which is better than
GoCardless - the owner never pastes a URL into somebody else's dashboard (§4.8).

## 3. Schema (`migrations/001_initial.sql`, prefix `atp_`)

All DDL idempotent - `CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`,
`CREATE INDEX IF NOT EXISTS` - per the module migration rule. `001` must stay correct
for a fresh install after `002` lands.

```sql
-- Non-secret settings (singleton). Credentials live in env vars, never here:
-- the database is included in backups.
CREATE TABLE IF NOT EXISTS "atp_settings" (
    "id" TEXT NOT NULL DEFAULT 'singleton',
    "enabled" BOOLEAN NOT NULL DEFAULT false,
    "payment_description" TEXT NOT NULL DEFAULT '',
    "environment" TEXT NOT NULL DEFAULT 'sandbox',
    "expires_in_minutes" INTEGER NOT NULL DEFAULT 30,
    "allow_card" BOOLEAN NOT NULL DEFAULT false,
    "webhook_endpoint_id" TEXT,
    "updated_at" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT "atp_settings_pkey" PRIMARY KEY ("id"),
    CONSTRAINT "atp_settings_singleton" CHECK ("id" = 'singleton')
);
INSERT INTO "atp_settings" ("id") VALUES ('singleton') ON CONFLICT ("id") DO NOTHING;

-- One row per checkout attempt.
CREATE TABLE IF NOT EXISTS "atp_payments" (
    "id" TEXT NOT NULL,
    "order_id" TEXT NOT NULL,
    "order_number" TEXT NOT NULL,
    "payment_request_id" TEXT,
    "status" TEXT NOT NULL DEFAULT 'PENDING',
    "amount" NUMERIC(12, 2) NOT NULL,
    "currency" TEXT NOT NULL,
    "return_path" TEXT,
    "created_at" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    "updated_at" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT "atp_payments_pkey" PRIMARY KEY ("id")
);
CREATE INDEX IF NOT EXISTS "atp_payments_order_id_idx" ON "atp_payments" ("order_id");
CREATE UNIQUE INDEX IF NOT EXISTS "atp_payments_payment_request_id_key"
    ON "atp_payments" ("payment_request_id");

-- One row per shop refund row. The primary key IS the idempotency guard Atoa
-- does not give us: id = the shop's refund row id, inserted BEFORE the call.
CREATE TABLE IF NOT EXISTS "atp_refunds" (
    "id" TEXT NOT NULL,
    "payment_request_id" TEXT NOT NULL,
    "atoa_refund_id" TEXT,
    "amount" NUMERIC(12, 2) NOT NULL,
    "currency" TEXT NOT NULL,
    "status" TEXT NOT NULL DEFAULT 'INITIATED',
    "created_at" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    "updated_at" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT "atp_refunds_pkey" PRIMARY KEY ("id")
);
CREATE INDEX IF NOT EXISTS "atp_refunds_payment_request_id_idx"
    ON "atp_refunds" ("payment_request_id");
```

`teardown` in the manifest: `["atp_refunds", "atp_payments", "atp_settings"]`.

**Backup gate:** this adds tables and columns, so `npm run test:backup-roundtrip`
must be run and must genuinely PASS (a skip is a fail). Export `OVH_SERVER`/
`OVH_USER`/`OVH_PASSWORD` from `/Users/chris/Git Local/Deskwell/Claude/.env` into the
shell for the run; never write them into this repo. No new column types are
introduced (`TEXT`, `BOOLEAN`, `INTEGER`, `NUMERIC`, `TIMESTAMP(3)` are all already
covered by `isSupportedUdtName`), and there are no sequences, so this should pass
first time - but it must be run, not assumed.

## 4. Phase 1 - hosted redirect

Ships alone and is useful alone. No third-party script on the checkout, no CSP change,
no domain whitelisting.

### 4.1 Settle the sandbox unknowns (blocking)

Against a sandbox key, confirm and write into `lib/atoa.ts` as comments:

1. **Units on `amount`.** Major or minor. Everything downstream depends on it.
2. **Sandbox addressing.** Which calls need `env=sandbox` and which infer it from the
   key.
3. **Currency scope.** Whether anything beyond GBP is worth claiming.

Do not write `toPence()`/`toMajor()` before (1) is answered.

### 4.3 `lib/env.ts` + `lib/settings.ts`

Four env vars, none required, none ever in the database. `isAtoaConfigured()` returns
true only when both the access secret and the webhook signing secret for the *current
environment* are present - a method that cannot confirm its own payments must not
reach checkout.

Settings hold the non-secret half. **Environment is a stored setting, not an env var**,
following the reasoning in `square-payment-for-shop/lib/settings.ts:5-12`: an
environment variable on a hosted project does not reach the running server until the
next deployment, so choosing "Production" did nothing until a redeploy and the panel -
reading back the environment the server could see - snapped the dropdown straight back
to Sandbox, which looked exactly like a failed save.

Two defaults that are decisions, not conveniences:

- **`expires_in_minutes` = 30.** Atoa's own default is `expiresIn` 180,000 ms - three
  minutes. Nowhere near enough to open a banking app, authenticate and approve. Left
  alone it produces dead payment links as routine behaviour. Always send `expiresIn`
  explicitly; never rely on the API default.
- **`allow_card` = false**, so `paymentMethod` goes up as `["PAY_BY_BANK"]`. Atoa also
  does cards, which on this platform sits next to Square doing the same job and drags
  in the `AUTHORIZED`/`CANCELLED` capture states. A setting rather than a hardcode
  because that is the platform rule.

`toEnvironment`/`toPaymentEntry`-style narrowing on read, per Square: anything
unrecognised falls back to the safe value, never `undefined as boolean`.

### 4.4 `lib/atoa.ts`

Bearer auth, typed at the boundary. Functions: `createPaymentRequest`,
`getPaymentStatus`, `cancelPayment`, `initiateRefund`, `getRefundStatus`,
`createWebhookEndpoint`, `listWebhookEndpoints`, `deleteWebhookEndpoint`. Every
response narrowed to a declared shape; an unknown status value throws rather than
falling through.

### 4.5 `lib/provider.ts`

```ts
export const atoaProvider: ShpPaymentProvider = {
  id: 'ATOA',
  label: 'Pay by bank',
  description: 'Pay directly from your bank account. No card needed.',
  logo: atoaLogo,
  confirmMode: 'auto',
  orderCreation: 'on-payment',
  settlesExistingOrder: true,
  refundMode: 'provider',
  isAvailable, getLabel, getClientFields,
  createIntent, confirmPayment, refundOrder, getRefundStatus,
}
```

`isAvailable` gates on credentials present **and** the owner having switched it on.
`settlesExistingOrder: true` is a promise about the whole settlement path, not just
`createIntent` - it means an unpaid bank transfer can be settled from the customer's
own order page (`modules/shop/lib/order-pay-online.ts`), so nothing here may assume a
shopper mid-checkout with a basket. `materialiseDraftOrder` returns an existing order
just as happily as it creates one, so going through it is what earns the claim.

`returnPath` is stored on the payment row, never read back out of the return URL -
that URL arrives through the shopper's browser, so a destination read from it is one
anybody can write. Validate it as a same-site path (`safeReturnPath` in
`gocardless-instant-bank-pay-for-shop/lib/provider.ts:26-30` - one leading slash, not
two; `//evil.example` is protocol-relative and a browser treats it as another site).

### 4.6 `lib/settle.ts`

Shared by the return route and the webhook; either may arrive first, both idempotent.

`paymentMatchesOrder(payment, order)` - amount and currency re-checked against the
order, or against the draft (`getCheckoutDraft`) where the order does not exist yet,
because the check has to happen **before** the order is brought into being. On a
mismatch: log loudly, leave unfulfilled, and do **not** mark it failed - on a completed
payment the money has gone, and telling the shopper their payment failed is its own
kind of wrong. Straight port of `gocardless.../lib/settle.ts:56-72`, with its test.

`markOrderPaid` is idempotent (no-op once PAID), so a replayed webhook cannot fulfil
twice. Never downgrade an order that is already PAID to awaiting.

### 4.7 Routes

`app/api/return/route.ts` - the `redirectUrl` Atoa sends the shopper back to. Confirms
server-side where it can, then redirects. Where there is no order (shopper backed out),
go back to `returnPath ?? '/shop/checkout'` with the basket intact, **not** to a
confirmation page for something nobody paid for. On success, hand off with the signed
receipt token (`signOrderReceiptToken`, `modules/shop/lib/order-receipt-token`) and
never an email address - a redirect URL lands in access logs, browser history and the
`Referer` header of every third party the confirmation page loads.

`app/api/webhook/route.ts` - verify `X-Atoa-Signature` as a **timing-safe** comparison
of the hex HMAC-SHA256 of the raw body against the dashboard signing secret. Read the
body with `request.text()` before parsing; a re-serialised body will not match.

> **Carry this over.** A failed batch must answer **500**, not 200. The GoCardless
> webhook originally swallowed errors and returned 200, which tells the provider the
> batch was handled - one transient database blip while settling was the last anyone
> heard of that payment, and the order sat AWAITING_CONFIRMATION for ever with the
> shopper's money gone. See the comment at
> `gocardless.../app/api/webhook/route.ts:70-78`.

`app/api/admin/settings/route.ts`, `app/api/admin/status/route.ts`,
`app/api/admin/register-webhook/route.ts` - all `shop.manage`.

### 4.8 Refunds

Insert the `atp_refunds` row **first**, keyed on the shop's refund row id
(`ShpRefundRequest.idempotencyKey`, which the shop refund route sets to that id). A
duplicate-key error means this refund has already been sent; return the existing
result and do not call Atoa again. Then re-validate currency and remaining refundable
amount before issuing - never trust the request alone.

Implement `getRefundStatus` so the shop's stale-PENDING reconciler resolves rows on
its own instead of reporting them to the owner. Three-valued: `unknown` is not a
failure, it means do not touch the row.

### 4.9 Admin settings tab

`components/admin/SettingsTab.tsx` on `shop.payments`: on/off, environment,
description (30-char counter, see §7.7), expiry, card toggle, connection status, and a
**Register webhook** button that calls `createWebhookEndpoint` and stores the returned
id in `webhook_endpoint_id`. Colours from semantic CSS variables only - no hex in
component chrome. Checked light and dark for AA contrast.

### 4.10 Tests, wiki, art

`lib/settle.test.ts` (`paymentMatchesOrder`), `lib/amount.test.ts` (the conversion,
once §4.1 answers it), `lib/webhook-signature.test.ts`, `lib/status.test.ts` (the
mapper, including the unreachable card states). `wiki/Pay-With-Atoa.md`, README,
`module-art.webp`, LICENSE, `package.json`.

## 5. Phase 2 - on-page dialog

### 5.1 The setting (`migrations/002_payment_entry.sql`)

```sql
-- Where the shopper authorises: on Atoa's own hosted page (a redirect away and
-- back), or in Atoa's dialog opened over this site's own checkout.
--
-- Defaults to 'redirect', and anything unrecognised reads as 'redirect'. It has
-- to: on-page needs the site's domain whitelisted in the Atoa dashboard, and no
-- existing shop has been asked to do that - so a default of 'on-page' would have
-- switched a working payment method off on somebody's live shop the moment they
-- updated the module.
ALTER TABLE "atp_settings" ADD COLUMN IF NOT EXISTS "payment_entry" TEXT
    NOT NULL DEFAULT 'redirect';
ALTER TABLE "atp_settings" DROP CONSTRAINT IF EXISTS "atp_settings_payment_entry_check";
ALTER TABLE "atp_settings" ADD CONSTRAINT "atp_settings_payment_entry_check"
    CHECK ("payment_entry" IN ('redirect', 'on-page'));
```

The settings tab presents two labelled choices with a sentence each, and says plainly
that on-page needs the domain whitelisting done first.

### 5.2 Branch the intent

One branch in `createIntent`, mirroring how GoCardless conditionally spreads its bank
picker (`gocardless.../lib/provider.ts:104`):

```ts
// redirect
return { approvalUrl: paymentUrl, providerOrderId: paymentRequestId }

// on-page
return { providerOrderId: paymentRequestId, clientFields: { paymentRequestId } }
```

**Never both.** `approvalUrl` present means shop redirects; `clientFields` present
means shop mounts the fields component. Returning both gives the checkout two
contradictory instructions.

`getClientFields()` returns `{ environment }` - the publishable, order-independent
half - so the component can boot the moment the method is picked. It cannot come from
the intent: creating one drafts an order, and that route refuses until the contact
details are filled in and every compulsory tickbox is ticked, so fields fed only by
the intent stay invisible until well past the point a shopper expects to see them.

### 5.3 `components/public/AtoaCheckoutFields.tsx`

Registered on `shop.checkout-payment-fields` under id `ATOA`. Contract:
`modules/shop/components/public/checkout-payment-fields.ts`. Draws a short line of
reassurance and calls `registerSubmit`. On "Place order" the submit function opens the
dialog and resolves when `onPaymentStatusChange` reports a terminal status, returning
`{ paymentRequestId }` to the confirm route.

Two rules from the contract, both load-bearing:

- **Trust the `config` argument, not the `config` prop.** "Place order" creates the
  intent and calls submit in the same breath without waiting for React to re-render,
  so the registered closure very often still holds the pre-intent config. Square's
  version of this showed shoppers "One or more of the arguments needed are missing or
  invalid" about a card they had filled in correctly.
- **The client never decides anything.** Whatever the dialog reports, `confirmPayment`
  asks Atoa server-side and re-checks amount and currency. The browser's word is a hint
  about when to look, nothing more.

Manifest gains:

```json
{ "point": "shop.checkout-payment-fields", "id": "ATOA",
  "import": "./components/public/AtoaCheckoutFields", "component": "AtoaCheckoutFields" }
```

### 5.4 Loading the SDK

Runtime script tag against a **pinned** version on unpkg:
`https://unpkg.com/@atoapayments/atoa-web-client-sdk@<x.y.z>`. Module `package.json`
dependencies are not installed by `scripts/checkout-modules.mjs`, so bundling the npm
package is not available - the script-tag route Square already uses
(`square-payment-for-shop/components/public/square-sdk.ts`) is the only one. Pinned
rather than floating: an unpinned CDN tag on a checkout page is arbitrary third-party
code that can change under you.

One shared loader module so two blocks on one checkout cannot each boot their own copy.
Type only the shape actually called - the SDK ships no types worth having and a
hand-written mirror of the whole thing would be a lie within a release.

`cspOrigins` in the manifest: `script` for unpkg, `frame`/`connect`/`img` for Atoa.
Scope as tightly as the dialog tolerates - Square's `frame: ["*"]` is a wildcard worth
not copying without cause. Generated into the CSP by
`scripts/generate-module-csp.mjs`.

Init shape:

```ts
const sdk = new AtoaWebSdk({
  environment: 'SANDBOX' | 'PRODUCTION',
  paymentRequestId,
  customerDetails: { email, phoneCountryCode, phoneNumber },
  onClose, onUserCancel, onPaymentStatusChange, onError,
})
sdk.showPaymentDialog()
```

### 5.5 Failure paths

Four callbacks, four distinct outcomes, none silent:

| Callback | Outcome |
|---|---|
| `onUserCancel` | Checkout exactly as it was, basket intact. Not an error. |
| `onClose` with no status | Same. |
| `onError` | Readable sentence on the checkout's error line via `onError` prop. |
| status `FAILED` | "The payment did not go through" + another go. |

Every message has to be one a shopper can read - "Your bank did not complete the
payment", not a status code. Throwing from the submit function stops the order and
shows the thrown message, so the message is the shopper-facing copy.

## 6. Light and dark

Atoa's SDK takes no theme, mode or appearance parameter (§0.1). The requirement splits:

**Ours, entirely** - the method row and its logo, the reassurance line, the trigger and
pending states, the error line, the scrim behind the dialog, and every pixel of the
settings tab. All on core's semantic CSS variables, correct in both themes, AA-checked
before ship.

**Atoa's, not ours** - the dialog interior. One dashboard brand colour, no dark
variant. If it renders in an iframe we cannot restyle it, and should not try.

What we actually do:

1. **Copy `isDarkBackdrop`** from
   `modules/square-payment-for-shop/components/public/backdrop.ts` - copy, not import.
   Atoa declares a dependency on `shop` and nothing else; reaching into a sibling
   module is an undeclared dependency. Bring its comments across; they are the record
   of two shipped bugs (light fields on a dark checkout, then dark fields on a light
   one).
2. **Measure the backdrop, do not read `data-theme`.** A site whose brand palette is
   dark paints a dark checkout while the attribute still says light. Walk up from the
   container to the first element with an opaque background and measure that, skipping
   anything painting an image or gradient over its own colour - `<body>` carries the
   owner's Theme colour and paints the real page colour over the top, which is exactly
   the bug. The attribute is the tie-breaker, not the answer.
3. **Give the module's own chrome both palettes** through the semantic variables, so it
   follows the site rather than guessing.
4. **Verify how the dialog renders** in sandbox - iframe or injected DOM. That single
   fact decides whether step 5 is possible at all.
5. **If injected DOM**, check our scrim and stacking sit correctly around it and
   nothing of ours bleeds in. **If iframe**, leave it alone entirely.
6. **Document the brand colour as an owner task** in the wiki: pick one that holds
   contrast on both a light and a dark checkout, because Atoa will use it on both.

Say this out loud in the release notes. An owner on a dark site should learn from the
documentation, not from a shopper, that the payment dialog follows their Atoa brand
colour rather than their site's theme. Silence reads as a bug in our module.

## 7. Risks

Ranked by consequence, not likelihood.

| # | Risk | Handling |
|---|---|---|
| 7.1 | **Amount units undocumented** | Hundredfold error on live money. Settled in sandbox at §4.1 before any conversion helper exists. Blocking. |
| 7.2 | **No idempotency key on refunds** | A retry could pay out twice. `atp_refunds` keyed on the shop's refund row id; the insert is the lock and happens before the call. |
| 7.3 | **Three-minute default expiry** | Dead links as routine behaviour. `expiresIn` always sent explicitly, owner-configurable, default 30 min. |
| 7.4 | **Pinned SDK on the checkout** | Third-party script on a payment page. Pin the version, scope the CSP, review on every bump. |
| 7.5 | **No idempotency on create either** | Double-submit makes two payment requests for one order. Unique index on `payment_request_id` + a per-order guard; reuse a live request rather than creating a second. |
| 7.6 | **Sandbox shares the production host** | Wrong key means live money. Environment is a stored setting, surfaced unmissably in the tab, sandbox as fallback. |
| 7.7 | **`notes` capped at 30 chars** | Validate and count down in the settings field rather than truncating silently at the API. |
| 7.8 | **Metadata frozen after creation** | Everything needed for reconciliation goes in at creation. Our own row is the source of truth regardless. |

## 8. Open questions

**For the owner:**

- **Does it earn its place next to GoCardless Instant Bank Pay?** Both are pay-by-bank.
  Atoa quotes roughly 0.6-0.7% + VAT with instant settlement, which may beat what
  GoCardless costs on this account - but that is a commercial comparison, worth doing
  before the build rather than after.
